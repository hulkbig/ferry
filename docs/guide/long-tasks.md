# 让 Agent 少停在半路

你希望交代一次任务，回来时工作已经推进了一大截。Ferry 负责其中的上游接入、选路和请求恢复：把临时故障尽量留在网关内处理，让 Agent 少停下来等你换线路。

这篇指南从一条已能正常调用的线路开始，为它添加恢复能力。还没启动实例？先完成[快速开始](quickstart.md)。

## 给客户端一个稳定入口

假设你常用的模型是 `work`。这是你在 Ferry 中创建的逻辑模型名，下面可以配置不同供应商、账号和实际上游模型。`work` 是示例，不是内置模型。

客户端只需知道三件事：Ferry 的推理地址、自己的 API Key，以及 `work`。以后增加备用账号、调整上游顺序或更换实际模型，都在 Ferry 中完成。

在 **模型与路由（Models & Routing）** 中创建或编辑逻辑模型，在路由里选择已有的 Provider 和准确上游模型。先保留禁用状态，完成路由检查后再启用。创建 Provider 时生成的同名逻辑模型也可直接使用。

## 给临时故障留一条退路

为模型安排首选和备用路由，并逐步设置允许触发恢复的条件。下面展示的是配置思路，实际选择由你的上游和任务要求决定：

| 遇到的情况 | 配置和预期行为 | 去哪里看结果 |
| --- | --- | --- |
| 首选线路连接失败或返回短暂 5xx | 在该步骤允许对应恢复条件，符合条件时尝试下一步 | 请求中的上游尝试和恢复原因 |
| 上游限流或连接容量暂满 | 在等待与恢复预算内排队或尝试可用连接／路由 | 队列、等待状态和恢复记录 |
| 上游接收了请求，却迟迟没有有效输出 | 为模型设置首输出等待上限，并允许对应超时恢复 | 首个输出超时及后续尝试 |
| 某个时段更适合用备用模型 | 设置时区、时间窗口和条件路由，先模拟再应用 | 命中的条件与最终路由 |

**首输出等待上限需要主动配置。** 模型的 `first_output_timeout_seconds` 为 `0` 时关闭，`1` 至 `7200` 秒时启用。它从每次上游尝试获得并发容量后开始计时，到首个有效文本、推理或工具输出为止；排队时间不计入，已经开始输出的长响应可以继续。上限应结合该模型的正常响应时间设置，慢推理不一定是故障。

设置超时不会自动增加恢复权限。检查路由的恢复条件、可用备用线路，再通过草稿校验、模拟和审阅应用变更。字段和请求格式见[管理 API](../../skills/ferry/references/management-api.md)。

条件路由也适合处理已知的分时价格差异：按你掌握的价格和时段设置偏好，Ferry 执行规则。它不会替你发现供应商的实时最低价。

## 备用线路，也要接得住任务

备用模型需要处理这次任务用到的协议和能力。普通聊天成功，还不足以证明工具续轮、推理或结构化输出可用。

添加上游时，选择实际需要的模型与原生协议，核对能力证据。Ferry 对选定组合进行有界探测，证据按端点、模型、协议和能力保存；探测可能产生调用费用。临时超时或 5xx 会保留为未知，不会直接判定模型永久不支持。

路由优先考虑精确匹配。默认兼容策略下，已注册的映射可以保留可执行路径，例如在没有精确候选时把并行工具要求映射到串行工具；映射和降级会留下记录。对必须精确保真的任务，在 API Key 或逻辑模型设置 `exact_only=true`，任一启用即生效。

三种文本协议的原生与转换路径分别有自己的约束，详见[协议行为](../protocol-fidelity.md)。图片生成与编辑使用独立的原生图片入口。

## 用一次真实任务确认它适合你

先用路由模拟检查候选、排除原因和规则命中，再用你实际使用的客户端运行一段包含工具调用与续轮的任务。观察一次请求的全过程：

1. **排队（Queue）**：请求是否在等容量，是否仍有运行中的尝试。
2. **请求（Requests）**：实际用了哪个上游、尝试了几次、何时等待、为什么换路，以及最终客户端结果。
3. **用量与费用（Usage & Billing）**：请求和恢复尝试的用量、价格依据与成本记录。

模拟不会发出推理请求，也不能证明真实账号和客户端已经兼容。若要主动制造限流、断连或超时，使用单独的测试实例或测试上游，保留真实任务的版本、配置、请求 ID 和结果。这样得到的是你自己的工作流证据。

Ferry 当前为源码候选；实现与离线回归覆盖不等于所有客户端和上游组合都已完成无人值守长任务验证。具体原生渠道的验证范围见[渠道支持](../provider-channel-coverage.md)。

## 恢复什么时候结束

一次长任务通常包含多轮请求。Ferry 在每次请求中处理上游恢复，客户端仍负责工具执行、任务规划和跨请求的续跑。

- **收到客户端取消**：停止等待与恢复。
- **预算用尽或没有兼容路线**：返回明确失败，记录原因，交由客户端处理。
- **已经向客户端提交可见输出**：保留当前流的归属，不拼接另一条模型流。之后的中断需要客户端根据实际结果处理。
- **账号无权限、请求无效或协议无法表达**：按具体错误与恢复规则处理，不把所有失败都当成临时故障反复重试。

恢复可能产生额外上游调用。设置 Key 的模型范围和预算，并结合请求记录检查实际效果。

## 让 Agent 帮你维护这条路

安装 [Ferry Skill](agent-skill.md)，给管理 Agent 独立的 Management Token。它可以读取请求证据、解释选路、运行模拟，再准备一份可审阅的配置变更。你在控制台使用的配置与记录，同样是它操作的依据。

可以从这样一项具体任务开始：

> 查看这次失败请求的尝试与选路记录，解释为什么没有恢复。检查现有备用路由，模拟一份调整方案，展示变更后会影响哪些请求。

从一个请求、一条恢复路由开始。验证后，再把同样的入口接到你每天使用的 Agent 上。
