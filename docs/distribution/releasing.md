# 公共发行流程

产品源码与协作入口为 `hulkbig/ferry`。发行版本必须绑定经过审核的源码、通过检查的提交和对应镜像摘要。

## 发布准备

1. 完成候选源码的产品检查、双架构镜像构建、空卷安装、首次请求、重启和备份恢复。对含请求历史的数据分别验证默认配置备份与显式 `-backup-history`：配置备份恢复后历史为空，完整备份恢复后历史保留，两者均保留管理员和客户端 Key。记录准确来源；本地验证不等于公共 CI 或发行验收。
2. 审核待公开源码、文档、许可证、图像及构建上下文，排除本地工作资料、部署环境配置和生产凭据。
3. 更新根目录 `compose.yaml` 的固定版本、双语 Docker 指南和 `docs/releases/<版本>.md`。公开用户应只需下载 Compose 文件并运行 `docker compose up -d`。
4. 准备 Docker Hub `bighulk/ferry` 和 GitHub `hulkbig/ferry`。发布凭据通过 GitHub secret `DOCKERHUB_TOKEN` 注入；安装用户无需任何维护者凭据。

## 时间窗口

北京时间工作日 22:00 至次日 08:00 前，才能创建公开 commit、push、操作公开 PR、触发对外可见的 Actions 或公开镜像／Release。使用实际提交时间，不回填时间或改写历史以满足窗口。

`scripts/release/public_window.py` 在实际镜像和 Release 写入前再次检查窗口，发布作业要求至少剩余 30 分钟，且作业超时为 20 分钟。检查窗口不会自动定时发布。公开 Actions 的手动触发和源码推送，也需要维护者在触发前检查时间。

## 发布准确源码

1. 在发行 checkout 审阅代码差异，确认来源和验证结果，在窗口内创建 commit。同步源码时保留产品文档、许可证及公开构建配置。
2. 将公开提交推送到目标分支，完成 PR 和必需检查。所有提交与操作必须位于窗口内；跨出窗口则保留状态，等下个窗口再继续。
3. 等待公开 `main` 上准确 SHA 的 **Product checks** 成功，再手动运行 **Public release**，填写稳定版本（例如 `0.1.0`）。

Public release 在 GitHub 托管的 AMD64 和 ARM64 Runner 上分别原生构建，检查空卷安装、鉴权、重启、在线备份及恢复，执行漏洞扫描并生成 SBOM。发布作业下载这些已经检查的镜像字节，不重新构建；核对 SHA、架构和同一 SHA 的完整 Product checks 结果后，才推送平台镜像并组合 manifest。

匿名拉取两个架构通过后，更新 `latest` 并发布 GitHub Release，附件包含固定版本 Compose、SBOM、manifest 和校验文件。精确版本与架构标签不覆盖；如发现同名标签，停止并对账，不盲目重跑或覆盖部分发行。

## 发布后验收

- 未登录访问 README、Release、安装文件及 Docker Hub 页面；图片使用公开 HTTPS 地址。
- 无源码、无登录、无内部凭据的环境拉取镜像，启动后完成管理员初始化和首次推理。
- 核对镜像 `/version` 的版本与公开提交；保存 manifest digest、平台摘要、公共检查及验收记录。
- 确认 Issues 和私密漏洞报告入口可用，再移除 README 与安装指南中的“发布准备”提示。

首次版本没有前一公共版本的升级证据。真实厂商验证、跨协议限制和暂未验证的账号驱动，按对应指南如实披露。
